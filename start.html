Start here

I don't know where to start

Open any AI engineering newsletter and you'll meet thirty words in a week: agents, MCP, Skills, RAG, embeddings, evals, harnesses, guardrails. It looks like thirty separate things to learn. It's really five layers of one system, and they're easiest to learn in a set order, ideally while you build one small project.

This page gives you the map, the order and the project. It takes about ten minutes to read. After that, the roadmap will take you through it week by week.

What is the field made of?

Think of an AI app as five layers, stacked one on top of the other. Each layer needs the one below it. Every term you hear belongs to one of these layers.

  1. 1

    Capabilities: what the agent can do

    The model itself, the instructions you give it, and the tools it can call. An agent is a model that decides for itself which tool to use next.

    models · prompting · structured outputs · tool calling · Skills · MCP
  2. 2

    Knowledge and context: what it knows

    A model only knows its training data and whatever you put in front of it. This layer is about choosing what goes into that limited space, and fetching it from your own documents.

    RAG · embeddings · reranking · context engineering · memory · knowledge graphs
  3. 3

    Execution and control: how it works through a task

    The loop that runs the model, carries out its tool calls, recovers from errors and knows when to stop or ask a human.

    workflows vs agents · orchestration · state · harnesses · human-in-the-loop
  4. 4

    Quality and trust: how you know it works

    Tests for systems whose answers vary from run to run, records of what the agent did and why, and limits on what it's allowed to do.

    evals · tracing and observability · guardrails · prompt-injection defence
  5. 5

    Production: how you run it for real

    Keeping it fast, cheap, secure and up when real people depend on it.

    deployment · caching · cost and latency · retries and fallbacks · governance

In what order should I learn it?

The rule behind this order is simple: learn each idea just before you need it. Each step below links to the roadmap weeks that teach it.

  1. Learn what a model is, and call one from code

    Start with what AI can and can't do, enough Python to write a short script, and how to prompt well. Then call a model from code and ask for structured output, meaning a reply in a fixed format such as JSON (a standard text format for data) that your program can read without guessing. Along the way, learn what a token is (a chunk of text, roughly three-quarters of a word, that models read and charge by).

    • week 1 · what AI can do
    • week 2 · Python
    • week 3 · prompting
    • week 4 · build with LLMs

  2. Give it knowledge it wasn't trained on

    Retrieval-augmented generation (RAG) means looking up the relevant passages in your own documents and handing them to the model with the question. It's like letting someone check their notes before they answer. You'll meet embeddings, which turn text into lists of numbers so that passages with similar meanings end up close together and can be found by meaning, not just by matching words.

    • week 5 · RAG

  3. Let it act, by building the loop yourself

    Build an agent by hand: call the model, run the tool it asks for, give it the result, and repeat until it's done. That loop is all an agent is. Build it once yourself before you use a framework, so the framework never feels like magic. Also learn the distinction that saves the most effort: many tasks need a fixed workflow (step A, then step B) and not an open-ended agent at all.

    • week 6 · your first agent

  4. Understand the model, then manage what it sees

    Now that you've watched an agent's input grow with every turn, two questions come up: how does the model actually work, and what should it be shown? Context engineering is the craft of filling the model's limited working space with the right instructions, retrieved passages, memory and tool results, and leaving out everything else.

    • week 7 · how LLMs work
    • week 8 · context engineering

  5. Package tools and know-how so any agent can use them

    The Model Context Protocol (MCP) is a standard plug for tools: write a tool once as an MCP server and any compatible agent can use it. Agent Skills package know-how, meaning folders of instructions and scripts an agent loads only when a task needs them. Both build on the tool loop from step 3, which is why they come after it.

    • week 9 · MCP fundamentals
    • week 10 · build an MCP server
    • week 11 · Agent Skills

  6. Make it dependable

    Evals are tests for AI systems: a set of inputs, plus a way to score the outputs. The score can come from exact checks, a rubric, or another model acting as judge. The harness is everything around the model: the loop, the tools, the sandbox that limits what commands can do, and the rules for retrying and stopping. Tune the harness and you change how good the agent is, often more than switching models would.

    • week 12 · evaluating agents
    • week 14 · harnesses

  7. Take it to production, and go deeper where you need to

    Learn to run agents for real: caching, cost and latency, retries, monitoring. If your documents hide answers that only appear when you connect facts across many files, look at knowledge graphs. Machine learning theory, the maths and the research frontier are worth it eventually, but they're optional. You can build good systems without them first.

    • week 15 · production
    • week 13 · knowledge graphs
    • weeks 16–18 · going deeper

Which habits should I start in week one?

Two topics sit late in most courses but pay off from the first week. Start them early, even in a rough form.

Keep a small test set from your first prompt

Write down 20 to 30 inputs and what a good answer looks like, and rerun them after every change. Without them, "it works now" means "it worked on the one thing I tried". A spreadsheet is enough to start. Week 12 turns it into proper evals.

Treat everything the agent reads as untrusted

Once an agent can call tools, a web page or document it reads can contain text that tries to give it new orders. This is called prompt injection. Give each tool only the permissions it needs, and ask a human before anything that deletes, sends or pays.

Record every run

Log each prompt, tool call and result. This kind of record is called a trace. When an agent goes wrong on step seven of twelve, the trace is the only way to see why.

What should I build?

Don't treat these as buzzwords to memorise. Build one small agent and let it grow as you go, so each new idea solves a problem you've already hit. Here's one example: an agent that writes and runs software tests. Any project you care about works the same way.

After Your testing agent can… And you can measure…
weeks 1–4 turn a written requirement into test cases, returned as JSON how many of your 20 sample requirements get sensible cases
week 5 find similar past test cases and reuse their patterns whether retrieval raised the score from the step before
weeks 6–8 run the tests itself, read failures and try again how often it finishes a task without help
weeks 9–11 reach your tools through MCP and follow your team's testing procedures as Skills whether a second agent can reuse the same tools unchanged
weeks 12–14 ask before anything destructive, with every run traced pass rate on a proper eval set, and the cause of each failure
week 15 run on a schedule for real users cost per run and time to finish

The last column matters most. A sentence like "the pass rate went from 60% to 78% after I added retrieval" means you understood what retrieval was for, which is worth more than having read about it.

You won't feel ready, and that's fine. Nobody does when the field changes this quickly. Open week 1 and write your first five test cases.
